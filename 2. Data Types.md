# 🟢 Kotlin Data Types — Complete Developer Guide

> **Level:** Beginner → Advanced &nbsp;|&nbsp; **Language:** Kotlin &nbsp;|&nbsp; **Focus:** Android Development

---

## 📌 Introduction

Every value in Kotlin has a **data type** — a classification that tells the compiler how much memory it needs, what operations are valid on it, and how it should be interpreted in binary.

Kotlin's type system is split into two broad families:

- **Basic types** — `Byte`, `Short`, `Int`, `Long`, `Float`, `Double`, `Boolean`, `Char`, `String`
- **Special types** — `Any`, `Unit`, `Nothing`, `Array`, collections (`List`, `Set`, `Map`), and nullable variants of all of the above (`Int?`, `String?`, …)

> Think of basic types as **labeled boxes of fixed size** — an `Int` box always holds exactly 4 bytes, a `Long` box always holds 8 — and the compiler refuses to let you put the wrong shape of value into the wrong box.

---

## 🚀 Why This Is Important

Choosing the right data type isn't a cosmetic decision — it's foundational to writing safe, fast, idiomatic Kotlin.

- ✅ It affects **memory & performance** — `IntArray` avoids boxing, `Array<Int>` doesn't
- ✅ It affects **correctness** — `Double` for money causes rounding bugs; `BigDecimal` doesn't
- ✅ It enables **null safety** — `Int` vs `Int?` is enforced at compile time, eliminating a huge class of crashes
- ✅ It drives **API design** — `Nothing`, `Unit`, and sealed types let the compiler enforce contracts for you
- ✅ It prevents **silent bugs** — Kotlin does **not** auto-widen numeric types like Java does

> 📱 **Android context:** Room column types, Retrofit/Gson response models, Compose state, and Bundle extras all hinge on getting data types right — a `Long` vs `Int` mismatch in a Room primary key is one of the most common production bugs in Android apps.

## 🧠 Concept Explanation

### Numeric Types

| Type | Size | Range | Literal Suffix |
|---|---|---|---|
| `Byte` | 8-bit | -128 to 127 | — |
| `Short` | 16-bit | -32,768 to 32,767 | — |
| `Int` | 32-bit | -2,147,483,648 to 2,147,483,647 | — (default for integers) |
| `Long` | 64-bit | ±9,223,372,036,854,775,807 | `L` |
| `Float` | 32-bit IEEE 754 | ~6–7 decimal digits precision | `f` / `F` |
| `Double` | 64-bit IEEE 754 | ~15–16 decimal digits precision | — (default for decimals) |

```
val a: Int    = 100          // 4 bytes
val b: Long   = 100L         // 8 bytes
val c: Float  = 1.5f         // 4 bytes, IEEE 754 single
val d: Double = 1.5          // 8 bytes, IEEE 754 double — default!
```

### Boolean & Char

- `Boolean` — exactly two values: `true` / `false`. No truthy/falsy coercion like JS — `if (1)` is a compile error in Kotlin.
- `Char` — a single 16-bit Unicode character, written in **single quotes**: `'A'`, `'7'`, `'\n'`. Not the same as a 1-character `String`.

### String

- `String` is **immutable** — every "modification" (`+`, `replace`, `uppercase()`) returns a **new** `String`.
- Backed by a `CharArray` internally; use `StringBuilder` for genuine in-place mutation.

### Arrays & Collections

| Type | Boxed? | Mutable? | Notes |
|---|---|---|---|
| `IntArray`, `LongArray`, `DoubleArray`, … | ❌ No | ✅ Yes (elements) | Primitive-backed, zero boxing overhead |
| `Array<Int>` | ✅ Yes | ✅ Yes (elements) | Generic array — boxes every element |
| `List<T>` | — | ❌ No (interface) | Read-only **view** — doesn't guarantee deep immutability |
| `MutableList<T>` | — | ✅ Yes | Adds `add()`, `remove()`, etc. |
| `Set<T>` / `Map<K,V>` | — | ❌ / ✅ variants | Uniqueness / key-value semantics |

### Special Types — `Any`, `Unit`, `Nothing`

- **`Any`** — the root of the Kotlin class hierarchy (like Java's `Object`), but leaner: only `equals()`, `hashCode()`, `toString()`. Every non-nullable type is a subtype of `Any`.
- **`Unit`** — Kotlin's equivalent of `void`, except it's a **real type** with exactly one value (the singleton object `Unit`). A function with no explicit return type implicitly returns `Unit`.
- **`Nothing`** — a type with **no instances at all**. Used for functions that never return normally (`throw`, `TODO()`, infinite loops) and as the type of `emptyList()`'s element. `Nothing` is a subtype of **every** type — that's what lets `throw Exception()` be used as an expression anywhere a value is expected.

### Nullable Types

```
var name: String  = "Riya"   // can NEVER hold null
var nickname: String? = null // CAN hold null — must be checked before use
```

Every type `T` has a nullable counterpart `T?`. The compiler forces you to handle the `null` case before accessing members — this single feature eliminates most `NullPointerException`s seen in Java/Android code.

### Unsigned Types

| Type | Range |
|---|---|
| `UByte` | 0 to 255 |
| `UShort` | 0 to 65,535 |
| `UInt` | 0 to 4,294,967,295 |
| `ULong` | 0 to 18,446,744,073,709,551,615 |

```kotlin
val age: UInt = 25u
val fileSize: ULong = 4_294_967_296uL
```

> ⚠️ Unsigned types have limited Java interop and are mainly intended for bit manipulation, low-level APIs, and ranges that are conceptually never negative (sizes, counts). Don't reach for them by default.

---

### Key Differences at a Glance

| Feature | `Int` | `Long` | `Float` | `Double` | `Array<Int>` | `IntArray` |
|---|---|---|---|---|---|---|
| Default literal type | ✅ Yes | ❌ needs `L` | ❌ needs `f` | ✅ Yes | — | — |
| Boxed in generics | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Always | ❌ Never |
| Implicit widening from smaller type | ❌ No | ❌ No | ❌ No | ❌ No | — | — |
| Can be `null` | ❌ (unless `Int?`) | ❌ (unless `Long?`) | ❌ | ❌ | depends on `T` | ❌ Never |
| Use for money | ❌ No | ⚠️ Minor units only | ❌ Never | ❌ Never | — | — |

### 3️⃣ Numeric Ranges & Overflow ⚠️

```kotlin
val max = Int.MAX_VALUE        // 2147483647
val overflowed = max + 1       // -2147483648 — wraps silently, NO exception!

val safeLong: Long = max.toLong() + 1   // 2147483648 — correct, using Long
```

> ⚠️ Kotlin does **not** throw on integer overflow by default. Use `Long`, `Math.addExact()`, or explicit range checks for values that could exceed `Int` capacity (IDs, timestamps, file sizes).

---

### 4️⃣ Explicit Type Conversion — No Implicit Widening!

```kotlin
val intValue: Int = 10
// val longValue: Long = intValue        ❌ Compile error! Type mismatch
val longValue: Long = intValue.toLong()  // ✅ explicit conversion required

val text = "42"
val parsed: Int? = text.toIntOrNull()    // ✅ null-safe parsing — null if invalid
val unsafe: Int = text.toInt()           // ⚠️ throws NumberFormatException if invalid
```

> Unlike Java, Kotlin **never** auto-widens a variable from a smaller numeric type to a larger one. You must call `.toLong()`, `.toDouble()`, etc. explicitly — this is one of the most common "Java habit" traps for new Kotlin developers.

---

### 5️⃣ Nullable Types & Null Safety

```kotlin
var city: String? = null
city = "Surat"

val length = city?.length          // safe call — null if city is null
val safeLength = city?.length ?: 0 // elvis operator — default fallback
val forced = city!!.length         // ⚠️ throws NPE if city is null — avoid!
```

---

### 6️⃣ `Any`, `Unit`, `Nothing` in Practice

```kotlin
fun logEvent(payload: Any) {        // accepts ANY non-null type
    println("Event: $payload")
}

fun printWelcome(): Unit {          // explicit Unit — same as omitting return type
    println("Welcome!")
}

fun fail(message: String): Nothing {
    throw IllegalStateException(message)   // never returns normally
}

val user = currentUser ?: fail("No user logged in")  // Nothing fits ANY expected type
```

---

### 7️⃣ `Array<Int>` vs `IntArray` vs `List<Int>`

```kotlin
val boxedArray   = arrayOf(1, 2, 3)        // Array<Int>  — boxes each element
val primitiveArr = intArrayOf(1, 2, 3)     // IntArray    — no boxing, faster
val list         = listOf(1, 2, 3)         // List<Int>   — read-only view

println(primitiveArr.sum())   // 6 — operates on raw int[] under the hood
```

> 📱 **Android tip:** Prefer `IntArray`/`FloatArray` over `Array<Int>`/`List<Float>` in performance-sensitive code (custom rendering, sensor data, game loops) to avoid GC pressure from boxing.

---

### 8️⃣ Type Checking & Smart Casts (`is` / `as`)

```kotlin
fun describe(value: Any): String {
    return when (value) {
        is Int    -> "Int: ${value + 1}"        // smart-cast to Int inside this branch
        is String -> "String of length ${value.length}"
        is Boolean -> "Boolean: $value"
        else      -> "Unknown type"
    }
}

val obj: Any = "hello"
val safe = obj as? Int   // null — safe cast, no exception
// val unsafe = obj as Int  ❌ throws ClassCastException
```

### 🔟 Sealed Class as an Algebraic Data Type

```kotlin
sealed class PaymentResult {
    data class Success(val transactionId: String, val amountCents: Long) : PaymentResult()
    data class Failure(val errorCode: Int, val reason: String) : PaymentResult()
    object Pending : PaymentResult()

fun handle(result: PaymentResult) = when (result) {
    is PaymentResult.Success -> "Paid: ${result.amountCents}"
    is PaymentResult.Failure -> "Failed: ${result.reason}"
    is PaymentResult.Pending -> "Waiting..."
    // no 'else' needed — exhaustively checked by the compiler
}
```

### 1️⃣2️⃣ Value Class (Type-Safe Wrapper, Zero Overhead)

```kotlin
@JvmInline
value class UserId(val raw: Long) {
    init { require(raw > 0) { "UserId must be positive" } }
}

@JvmInline
value class Money(val cents: Long) {
    operator fun plus(other: Money) = Money(cents + other.cents)
    override fun toString() = "₹${cents / 100}.${(cents % 100).toString().padStart(2, '0')}"
}

val price = Money(4999) + Money(500)
println(price)   // ₹54.99
```

> 💡 `value class` gives you a distinct, type-safe data type at **compile time** with no extra heap allocation at runtime in most cases — perfect for IDs, currency, and other primitive-obsession fixes.

## ⚠️ Common Mistakes

### ❌ Mistake 1 — Assuming Kotlin auto-widens numeric types like Java

```kotlin
val i: Int = 10
val l: Long = i        // ❌ Compile error!
val l: Long = i.toLong() // ✅ Correct
```

✅ **Fix:** Always convert explicitly with `.toLong()`, `.toDouble()`, etc. — Kotlin only special-cases **literal constants**, never variables.

---

### ❌ Mistake 2 — Using `Double` for money

```kotlin
val price = 19.1 + 0.05      // 19.15 looks fine here...
val total = 0.1 + 0.2        // 0.30000000000000004 ⚠️ — NOT 0.3!
```

✅ **Fix:** Use `Long` (minor units like cents) or `java.math.BigDecimal` for any monetary or precision-critical calculation.

---

### ❌ Mistake 3 — Comparing boxed `Int?` with `===` instead of `==`

```kotlin
val a: Int? = 200
val b: Int? = 200
println(a == b)    // true  ✅ structural equality
println(a === b)   // false ⚠️ — 200 is outside the cached Integer range (-128..127)!
```

✅ **Fix:** Always use `==` for value comparison. Reserve `===` for genuine reference-identity checks.

---

### ❌ Mistake 4 — Treating `Array` equality like `List` equality

```kotlin
val arr1 = arrayOf(1, 2, 3)
val arr2 = arrayOf(1, 2, 3)
println(arr1 == arr2)               // false ⚠️ — Array uses referential equality!
println(arr1.contentEquals(arr2))   // true  ✅ — structural comparison

val list1 = listOf(1, 2, 3)
val list2 = listOf(1, 2, 3)
println(list1 == list2)             // true ✅ — List overrides equals() structurally
```

✅ **Fix:** Use `contentEquals()` (or `contentDeepEquals()` for nested arrays) — never `==` — when comparing `Array` contents.

---

### ❌ Mistake 5 — Forgetting that `Int` overflow is silent

```kotlin
fun calculateTotalCents(items: List<Int>): Int {
    return items.sum()   // ⚠️ if this overflows Int.MAX_VALUE, it silently wraps negative!
}
```

✅ **Fix:** Use `Long` for any accumulator that could plausibly exceed ~2.1 billion (money totals, byte counts, large user counts).

---

## 💡 Pro Tips

- 💡 Default to `Int` and `Double` — only reach for `Byte`/`Short`/`Float` when memory layout genuinely matters (large arrays, native interop, sensor data)
- 💡 Use `IntArray`/`LongArray`/`FloatArray` instead of `Array<Int>`/`List<Long>` in hot loops — avoids boxing entirely
- 💡 Always model money as `Long` (minor units) or `BigDecimal` — never `Float`/`Double`
- 💡 Prefer `sealed class`/`sealed interface` over plain `enum class` when each variant needs to carry different data
- 💡 Use `@JvmInline value class` to wrap primitive IDs (`UserId`, `OrderId`) for compile-time type safety with no runtime cost
- 💡 Use `as?` + elvis (`?:`) instead of unsafe `as` to avoid `ClassCastException` crashes
- 💡 Be explicit with literal suffixes (`L`, `f`, `u`, `uL`) — don't rely on inference when the type matters for a function signature
- 💡 Use `.toIntOrNull()` / `.toDoubleOrNull()` instead of `.toInt()` / `.toDouble()` whenever input could be malformed (user input, network data)
- 💡 Reach for `BigInteger`/`BigDecimal` (from `java.math`) the moment you need arbitrary precision beyond `Long`/`Double`

## 🎯 Interview Questions & Answers

---

### Q1. What are the basic data types in Kotlin?

> **Answer:**
> Numeric types (`Byte`, `Short`, `Int`, `Long`, `Float`, `Double`), `Boolean`, `Char`, and `String`. Kotlin also has special types `Any` (root type), `Unit` (void-equivalent), `Nothing` (no-value type), and the `Array`/collection family.

---

### Q2. Does Kotlin support implicit numeric type conversion like Java?

> **Answer:**
> **No.** Java implicitly widens `int` to `long` to `double`, but Kotlin requires explicit conversion (`.toLong()`, `.toDouble()`) for **variables**. The only exception is literal constants in a context with a known expected type (e.g. `val l: Long = 5` compiles because `5` is a literal, not a variable).

---

### Q3. What is the difference between `Int` and a boxed `Integer` in Kotlin?

> **Answer:**
> On the JVM, `Int` compiles down to the primitive `int` whenever possible (non-nullable, non-generic context). It gets **boxed** into `java.lang.Integer` automatically when used as `Int?`, stored in a generic collection (`List<Int>`), or passed where `Any` is expected — this boxing has a small but real performance cost.

---

### Q4. What is `Unit` and how does it differ from Java's `void`?

> **Answer:**
> `void` in Java is the absence of a return value — it isn't a real type and can't be used as a generic type argument. `Unit` in Kotlin **is** a real type with exactly one instance (the singleton `Unit` object), so it can be used as a type parameter (e.g. `Function0<Unit>`), enabling Kotlin's functional features to treat "returns nothing" uniformly with everything else.

---

### Q5. What is the `Nothing` type and where is it used?

> **Answer:**
> `Nothing` has **zero instances** and represents "a value that never exists" — used for functions that never complete normally (`throw`, infinite loops, `TODO()`). Because `Nothing` is a subtype of every other type, an expression of type `Nothing` (like `throw Exception()`) can be used anywhere a value is expected, e.g. `val x = nullableValue ?: throw IllegalStateException()`.

---

### Q6. What is the difference between `Array<Int>` and `IntArray`?

> **Answer:**

| | `Array<Int>` | `IntArray` |
|---|---|---|
| Backing | `Object[]` of boxed `Integer` | raw `int[]` |
| Boxing | ✅ Every element boxed | ❌ No boxing |
| Memory | Higher (object headers per element) | Lower (contiguous primitives) |
| Use case | Generic code, mixed-type needs | Performance-critical numeric data |

---

### Q7. What's the difference between `as` and `as?`?

> **Answer:**
> `as` performs an **unsafe cast** — it throws `ClassCastException` if the cast is invalid. `as?` performs a **safe cast** — it returns `null` instead of throwing if the cast fails. Prefer `as?` combined with the elvis operator (`?:`) for cast operations where failure is a normal possibility.

---

### Q8. How do smart casts work with `is`?

> **Answer:**
> After an `is` check, the compiler automatically treats the variable as the checked type within that scope — no explicit cast needed — **as long as the compiler can prove the value can't change** between the check and the use. This works reliably for `val` and local `var`, but fails for mutable class-level `var` properties (since another thread could theoretically change the value in between).

---

### Q9. What is the difference between `List` and `MutableList` regarding immutability?

> **Answer:**
> `List` is a **read-only interface** — it simply doesn't expose `add()`/`remove()`. It does **not** guarantee the underlying object is truly immutable: if the same backing `ArrayList` is also referenced as a `MutableList` elsewhere, mutations through that reference will be visible through the `List` view too. For genuine deep immutability, use a library like `kotlinx.collections.immutable`.

---

### Q10. When should you use unsigned types (`UInt`, `ULong`, etc.)?

> **Answer:**
> Reserve them for cases where a value is **conceptually never negative** and where bit-pattern semantics matter — bitmasks, low-level byte/size handling, or interop with native/C APIs. For everyday business logic (counts, IDs, prices), regular signed types with explicit validation are usually clearer and have far better interop with Java libraries and serialization frameworks.

### Core Rules to Remember

- ✅ Kotlin **never** auto-widens numeric variables — always convert explicitly
- ✅ Never use `Float`/`Double` for money — use `Long` (minor units) or `BigDecimal`
- ✅ `IntArray` ≠ `Array<Int>` — one boxes, one doesn't
- ✅ `==` is structural equality (calls `equals()`); `===` is referential identity
- ✅ `Array` uses **referential** `==`; use `contentEquals()` for structural comparison
- ✅ `Nothing` is a subtype of every type — that's how `throw` works as an expression
- ✅ Prefer `value class` to wrap primitive IDs for compile-time type safety at zero cost

### 03 · `Int` — the default whole-number type

```kotlin

```

> `Int` is Kotlin's default integer type — use it unless you have a specific reason not to.

### 04 · `Long` — for large numbers and timestamps

```kotlin

val fileSizeBytes = 5_368_709_120L   // 5 GB, needs L suffix
```

> Always use `Long` for timestamps, IDs at scale, and file sizes — `Int` overflows around 2.1 billion.

### 05 · `Float` — single-precision decimal


### 06 · `Double` — default decimal type

### 07 · `Boolean` — true/false only

```kotlin
val isLoggedIn: Boolean = true

// if (1) { }  ❌ Compile error — no truthy/falsy coercion in Kotlin
```

> Kotlin has zero implicit conversion to Boolean — conditions must be actual `Boolean` expressions.

### 08 · `Char` — single Unicode character

### 09 · `String` — immutable text

```kotlin
println(nan == nan)         // false ⚠️ — NaN is never equal to itself per IEEE 754
println(nan.isNaN())        // true  ✅ — correct way to check
```

> Always use `.isNaN()` — never `==` — to detect `NaN` values.

### 90 · `typealias` provides zero type safety

### 99 · `===` on `String` can be `true` due to interning — but never rely on it

```kotlin
val a = "hello"

println(a === b)   // true — compile-time string literals are interned/pooled

```

### 100 · Choosing the right type — the ultimate decision summary

```kotlin
// ✅ All of these reflect correct, idiomatic Kotlin type choices:

val userId: Long           = 100245L        // IDs at scale → Long
val priceInCents: Long     = 199900L        // money → Long minor units, never Double
val rating: Double         = 4.7            // general decimal → Double
val isPremium: Boolean     = true           // binary state → Boolean
val initials: Char         = 'R'            // single character → Char
val tags: List<String>     = listOf("new")  // read-only collection → List
val pixelBuffer: IntArray  = IntArray(1080) // large numeric buffer → primitive array
@JvmInline value class OrderId(val raw: Long)  // domain ID → value class

// The golden rule:
// → Pick the narrowest, most specific type that matches the DOMAIN, not just the value
// → Let the compiler — not a runtime check — catch type mistakes
```

> Choosing a data type is a **design decision**, not just a syntax choice — it's the first line of defense against an entire category of bugs.
